# CHNUG #5

A compact, three-talk program from the Swiss network user group (Cisco Wallisellen, 12 Nov 2026) — and unusually dense for its size: one production AI-plus-Network-as-Code rollout with real numbers, one open-source eVPN control plane running a live ISP network, and one of the more honest treatments of declarative configuration management available. All three talks had substantive slide decks to draw on; no abstracts were published, so the write-ups below are grounded in the actual material.

## Core

### Let AI Break the Lab: Network as Code in the Real World

**Links:** [Slides](https://chnug.ch/chnug005/slides/chnug005-02-let-ai-break-the-lab-network-as-code-in-the-real-world.pdf) · [Recording](https://www.youtube.com/watch?v=J9vZReJpqxU)

Speakers: Patrick Mosimann (Cisco), Dawid Bednarczyk (Cisco CX)

- **Why**: This is the first talk in the program that directly addresses the question every network org is wrestling with in 2026: how do you let AI agents near a production network without burning it down? The answer here is not "AI runs your network" — it is a concrete, measured case study of AI writing almost every change while a deterministic pipeline holds the keys. For a PM thinking about automation and AI-for-infrastructure, this is a rare empirical data point rather than a demo.
- **What**: A full Network-as-Code (NaC) method — YAML data model in Git, validation, Terraform plan/deploy, tests generated from the same model — combined with AI agents (Claude Code CLI) drafting changes, deployed in a real rollout: a European insurer, ~10 office sites in two countries, ~350 access switches, ~1,200 APs, ~4,400 users, migrating to Catalyst Center + ISE (802.1X/EAP-TLS everywhere) + SD-WAN, all as code. The deck gives real progress metrics: ~860 commits, 121 pipeline runs, 108 AI Research→Plan→Implement cycles, 36 transcribed meetings, with first production push in Nov 2026. Crucially, it includes a failure taxonomy: of 121 pipeline runs, 75 failed (37 device-rejects-the-apply, 10 plan-time errors, 9 device-not-in-inventory, 13 failure classes total), which AI itself read and turned into an 8-gate local pre-check.
- **How**: Every AI idea becomes a diff to a YAML file; the merge request is the change ticket (diff, plan, tests, approver). The pipeline stages — validate (nac-validate, Yamale schema + Python rules), plan (terraform), human review, deploy, test (nac-test Robot templates rendered from the same YAML) — are the same ones a human change goes through. Two key operational patterns: (1) a lab environment with real hardware where AI has auto-apply and is *allowed to fail*, versus production with no shared state and mandatory senior-engineer approval; (2) direct read-only, audited AI access to the lab (RADKit/Cisco IQ), which turned a day-long human capture-script relay into a minute-long loop — with concrete results like reproducing a failing template in the lab and finding a 343-character description against a 255 limit. Failover tests improved from 5–6 min outage to 0–1 lost pings (core, over four days and six code-made fixes) and from 5:17 min to ~9 s (WAN edge, same day). Six "landmines" caught before production are catalogued — a silently-unloaded validator schema (0 errors reported vs 129 real findings), an unpinned Terraform provider breaking the pipeline overnight, a risk-score gate that never fired, lab IPs in template defaults, an unsupported controller split, and one manual click that a redeploy dropped.
- **Where applicable**: The *method* is deliberately vendor-agnostic — any platform with an API and a Terraform provider works, and the open-source tools (nac-validate, nac-test, MPL-2.0 on GitHub) are public. But the worked examples and the case study are Cisco-stack specific (Catalyst Center, ISE, SD-WAN, ACI, NX-OS, Meraki models), and there is a Cisco CX services layer ("Services as Code", 300+ deployments claimed) — so read it as a strong operational lesson with a services pitch attached, not a neutral framework. The honest-caveat slide is worth internalizing: "AI speeds up everything you control. Only that" — tickets in other teams' queues, admin rights, licences and firewalls remained the bottleneck.

### VPP: eVPN Control Plane

**Links:** [Slides](https://chnug.ch/chnug005/slides/chnug005-03-vpp-evpn-control-plane.pdf) · [Recording](https://www.youtube.com/watch?v=ay8ms5fUPbg)

Speakers: Pim van Pelt (IPng Networks)

- **Why**: This is the physical/software fabric talk of the evening, and it matters well beyond its scale. It demonstrates that a fully open-source EVPN fabric — FD.io VPP dataplane plus a Bird2 control plane — is running in production at a real ISP (AS8298, 22 VPP/Bird routers, ~2,200 adjacencies on the FLAP exchange), interoperating with vendor gear, and scaling to DPU-based deployment. For anyone thinking about white-box/data-plane-programmable DC fabrics, BGP EVPN internals, or DPU-hosted networking, this is a working reference implementation, not a lab curiosity.
- **What**: An eVPN control and management plane for VPP, in three acts: (1) the building blocks — bridge domains, BVIs, VxLAN tunnels, split-horizon groups, disabling learn/flood on tunnel interfaces; (2) a custom Bird protocol (`vppevpn`, a patch on Bird 2.20, source on git.ipng.ch) that speaks BGP eVPN NLRI (RFC 7432/8214/9136), receives IMET and MAC routes, programs VxLAN tunnels and the VPP L2FIB, announces the local router's IMET/MACs, and reconciles VPP state vs the Bird table on a scan interval; (3) `vpp-evpn`, a management plane: an `epvnd` daemon running on Bluefield DPUs (Ubuntu/Debian, VPP inside), a central registry, gRPC client, and SolidJS WebUI. Requirements stated explicitly: O(100) routers, O(1,000) L3 subnets, O(10,000) P2MP L2 segments, 40 Mpps/100 Gbps per node, automated failover — with a Bird table of 4,803 routes / 1,601 networks shown live, and interop demonstrated against Arista EOS (with Juniper, Nokia, Centec, Cisco shown as peers). VPP brings Maglev load balancing, IPSec, WireGuard and MACsec along for free.
- **How**: Control/data plane separation in the classic style: Bird handles BGP (iBGP route-reflector clients exchanging eVPN NLRI, RD/RT, VNI, PMSI/VTEP addresses, RFC 5512 encapsulation extended communities) while VPP does the forwarding (100Mpps+/100Gbps+ on commodity x86 via DPDK/RDMA/VirtIO input nodes). The BVI is paired to Linux via LinuxCP (`bvi1000` ↔ tap `bvi-test`), so the host kernel sees a normal interface with IPv4/IPv6 addresses. `epvnd` adds CARP/HSRP-style healthchecking (multicast IPv6 probes on the eVPN segment, unicast to the internet), is restart-safe and reentrant (reconfigures Bird or VPP if they crash), and can move BVIs between DPUs for maintenance.
- **Where applicable**: Broadly applicable as an architecture, with caveats: the Bird `vppevpn` protocol is a personal patch against Bird 2.20, not mainline, so you inherit the maintenance burden; the scale targets and hardware (Bluefield DPUs) reflect a small ISP/operator context, not hyperscale DC; and the whole stack is self-operated — this is a build-it-yourself option for shops that want open-source end-to-end or DPU-resident L2/L3 services, not a product.

### From Configuration Tasks to Declarative Intent with Ansible

**Links:** [Slides](https://chnug.ch/chnug005/slides/chnug005-04-from-configuration-tasks-to-declarative-intent-with-ansible.pdf) · [Recording](https://www.youtube.com/watch?v=isj4vHPUswM)

Speakers: Tomas Horyl (Narrowin)

- **Why**: Most "declarative network automation" talks stop at happy-path Jinja2. This one goes where the real difficulty lives: what happens when defaults, profiles and host exceptions compose; who owns a setting your inventory doesn't mention; and what each platform's validation actually *proves*. For a PM who cares about configuration management at scale, the validation-matrix table alone justifies the watch.
- **What**: A five-stage architecture — declared intent → transformation → native configuration → deployment → device state — implemented in ordinary Ansible inventory, contrasted across three platforms: Cisco IOS (complete-file replacement, the running config decides undeclared settings), Nokia SR Linux (path-scoped update/replace/delete, the target path decides), and Cumulus NVUE (PoC; the declared NVUE root is authoritative, omitted config reverts to defaults). Intent is expressed as `update`/`delete` dicts in group_vars/host_vars — inherited group-first, host-last, with explicit deletion (a `{}` value removes an inherited command). The talk includes an offline renderer test harness (given known inputs, run the renderer with no SSH, compare to expected artifacts), per-platform diff/confirm flows (IOS contextual config diffs; optional rollback timer with auto-cancel), and — unusually honest — a per-platform table of validation blind spots (e.g. IOS: no general argument check, invalid arguments may reach replacement; NVUE: unknown final leaves can pass, types/dependencies unchecked). A closing example shows a correctly-applied configuration expressing the wrong design (trunk allows 10,30 while the endpoint is on VLAN 20): automation can faithfully apply a wrong intention.
- **How**: Declared intent lives in inventory; a Python filter transforms it to native CLI (replacing the composition pressure of Ansible templates that become "a program inside inventory"); transformation is deliberately separated from deployment so rendering rules can be tested without touching a switch; deployment machinery is reused across features by changing only the native config data, within each platform's native contract (not a universal API); each stage adds its own checks — fixture tests, device diffs, apply results — and the talk is explicit that none of them proves traffic works, so service verification stays a distinct step. The backup slides show a full CVD-style Cisco campus fabric (OSPF, PIM, BGP l2vpn evpn with VxLAN encap, bridge domains, BDI interfaces) reconciled in ordered group layers via a single role and serial play.
- **Where applicable**: General technique, multi-platform by construction (IOS and SR Linux are worked implementations; NVUE is a PoC), tested against containerlab topologies. Context is narrowin's IT/OT critical-infrastructure practice (energy, healthcare, utilities), which explains the emphasis on ownership boundaries and gradual brownfield adoption (baseline-as-source vs running-snapshot-as-source for unowned settings). Implementation effort is not eliminated — the speaker is explicit that "the implementation work has not disappeared" — but the responsibilities are cleanly shared and the machinery is reusable.

## Themes

- **AI enters the network change loop, but code is the guardrail**: The recurring pattern across the program is probabilistic AI drafting deterministic diffs. Every AI contribution lands as a merge request that a person reads, approves, and ships through the same pipeline a human change uses — "no change without a diff" as the organizing principle.
- **Network-as-Code is maturing into testable pipelines**: YAML data models as the single hub, with validation (schema, business rules, gitleaks), plan review, and tests rendered from the same model as first-class pipeline stages — in both the Cisco NaC toolchain and the narrowin Ansible framework. The lab is treated as a cheap place to fail, deliberately.
- **Open-source dataplane + control plane reaching production credibility**: VPP + Bird running a real AS with vendor interop (Arista, Juniper, Nokia, Cisco, Centec) and DPU deployment signals that fully self-built EVPN fabrics are a viable alternative path, not just research.
- **Honest accounting of failure and validation limits**: The strongest material in this program is negative results stated plainly — 75 of 121 pipeline runs failed, six landmines caught before production, per-platform tables of what each validation step does and does not prove, and the observation that "AI speeds up everything you control. Only that."
- **Ownership semantics of configuration are the hard problem**: Both the Ansible talk and (via terraform plan deltas and no-destroy policies) the NaC talk wrestle with the same question: what happens to a setting nobody declared — and the answer differs by platform (complete-file vs path-scoped vs root-authoritative), which is a decision practitioners must make consciously.
